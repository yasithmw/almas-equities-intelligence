01The bottleneck today

Every answer waits on someone to build it

Research and reporting demand keeps climbing while analyst hours stay flat. The work that produces an answer is manual, one-off, and easy to get subtly wrong, so the gap widens every quarter.

01

Answers wait in a queue

A number or a dashboard means waiting on someone to pull the data and build it, often past the point where the question still matters.

02

Analysts dig instead of decide

Skilled people spend the day hunting and cleaning data in spreadsheets, not making the judgement calls only they can make.

03

Recurring work is rebuilt from scratch

The same questions get a fresh, one-off build every time. Nothing compounds, and the same effort is spent twice.

04

Bad data slips through

Stale prices, missing dividends and broken corporate actions can quietly reach a client report before anyone notices.

05Access & Filtering

Every query the agents write is narrowed to the person who asked it, before it runs. This happens on every question, automatically, and there is no unfiltered view to fall back to.

  1. The question

    Someone types it in plain words, from any desk.

  2. Who is asking

    Their Microsoft sign-in travels with the question, so the platform knows who it is for.

  3. The narrowing

    A filter for that person’s access is added to the query, server side, before it runs.

  4. What comes back

    Only the rows that person is cleared to see. Never anyone else’s.

Enforced in three places, independently
The query

An agent can ask for a whole table. What actually runs against the database is cut down to that person’s rows first.

The tables

An agent cannot ask for what it never sees. Tables beyond that person’s access are removed before the question reaches it.

The tools

Each agent is handed only the actions its own job needs, so there is no route around the first two.

A missing rule denies everything, so a configuration mistake returns no data rather than the wrong data.

04Beyond the tools you already have

Why this is not another BI dashboard

It answers questions nobody built a view for, follows how your data actually connects, and keeps every answer inside the access of the person who asked.

The new question

A dashboard only answers the question it was built for

Every genuinely new question means someone specifies it, models it, and builds a view. Here the question itself is the interface: the agents plan the work, write the queries, and compose the chart or the whole dashboard on the spot, then keep it if you want it again.

The context

A query assistant does not know how your world connects

A query assistant writes against a model someone has already defined for it, and has no view of how an index, a sector, a company and a client account relate to each other. The knowledge graph holds those relationships, so “peers in the same index” or “this client’s sector exposure” resolves correctly instead of matching on a name.

The check

Nothing in a BI stack argues with its own answer

A generated query returns whatever it returns. Here a second agent is set against the draft to try to break it, the widgets are cross-checked for agreement, and failing data is quarantined upstream before it can reach an answer at all.

The governance

Your definitions and your controls live in one place

Metric definitions, data-quality rules, the knowledge graph, agent behaviour and access scoping are all configured in one admin portal, with two-person approval on every change and a full audit trail. In a typical BI estate that logic is scattered across reports, spreadsheets and people.

Capability 02

The knowledge graph

Context a query tool does not have

Your tables are only part of the picture. The platform keeps one graph that merges four kinds of knowledge, stitched together on the same entities, so a question can travel from a number in a table to the document that explains it and the house rule that qualifies it. Each kind is a lens you can switch on and off over the same canvas.

01Data lens

Your Fabric model as nodes and edges: securities, client accounts, trades, prices, dividends and corporate actions, down to individual rows.

At Almas“The banks” resolves to COMB, HNB, SAMP and NTB through the sector edge, not through a text match on the word bank.
02Knowledge lens

Concepts and facts extracted from the documents you upload, each one attached to the table, sector or security it actually describes.

At AlmasA CSE circular announcing a rights issue attaches itself to HNB, so an answer about HNB can quote the circular and its page.
03Memory lens

Your house definitions and working memory, written once in the admin portal and applied to every answer from then on.

At AlmasTurnover excludes crossings. Reporting is in LKR. A dealer sees their own book and nobody else’s.
04Activity lens

Who asked what, in which thread, and which chart came out of it, with the lineage between them kept.

At AlmasManagement can see which questions the desks are actually asking, and compliance can see what a given dealer was shown.

Capability 03

Client segmentation

Who is in your book, by behaviour

Every account in your book still carries the category it was given the day it opened. This groups them by how they actually trade instead, describes each group in words a desk can use rather than handing over a number, and keeps every run, so you can see which accounts moved between them.

01Behaviour, not the tag on the account

Accounts are grouped on how often they trade, how long they hold, the size of their tickets and the instruments they favour. The platform also proposes measures you do not already store, worked out from the same records.

At AlmasAn account opened as ordinary retail in 2019 that now turns over daily shows up where it belongs, not where it was filed.
02Grouped more than one way, then cross-checked

The same accounts are grouped several separate ways, using different reasoning each time. An account that lands in the same group across those passes is firmly placed, and where they disagree it goes to the closest fit and is marked as such.

At AlmasA relationship manager can see which part of a call list is solid and which part is a judgement call, before picking up the phone.
03Named and explained in plain words

Each group arrives already named and written up, built strictly from the handful of features that define it and the figures that separate it from the rest of the book. Your team can keep the name or change it.

At AlmasThe group that holds for months and buys around declaration dates is handed over described that way, not as a number for someone to work out.
04Movement between segments

Every published run is kept, and each account carries its own history, so a move from one segment to another is recorded rather than written over.

At AlmasSee which active clients drifted towards dormant this quarter, and whose book each of them sits in.
Capability 04

Data quality and quarantine

Nothing reaches an answer unchecked

An answer is only as good as the numbers under it, so this is a standing part of the platform rather than a report someone runs at month end. Checks you configure run on their own schedule against your own tables, and what they catch is held back rather than quietly averaged in.

01Checks on a schedule

Checks are configured per table and column and then run on a schedule, so a break is found by the platform rather than by whoever happens to notice a number looks wrong.

At AlmasA stale last price on a thinly traded counter is caught before it values a client’s holding.
02A gate in the pipeline, not in the app

A row that fails a blocking check is stopped on its way into the layer the agents query, so an answer cannot be composed from it at all. The guard sits in the pipeline, so it holds whatever route the data came in by.

At AlmasA dividend that was never declared in the source cannot quietly understate a yield screen.
03A review queue, with the fix drafted

Every held row is recorded with the rule it broke and the row itself, and an agent drafts the correction. Your team applies that fix, ignores the row, or drops it, and the decision takes effect on the next run.

At AlmasThe back office corrects a corporate-action mismatch once, and the corrected row goes through on the next run.
04Try it before it blocks anything

The guard can run in preview, listing every row it would have stopped without stopping any of them. You see what it would catch, and what that would cost you, before a single check goes live.

At AlmasRun it over a quarter of history during the pilot, then decide together which checks are worth enforcing.

06Security and where it runs

Built to hold a client’s book

In a platform like this, security is settled by architecture rather than by a list of controls added afterwards. Four decisions carry it.

A tenant of your own

An Azure tenant and subscription belonging to Almas, built from version-controlled code. No database, cache or key store is shared with another client.

Your data is never extracted

Nothing is exported into a vendor’s warehouse. Your sources are brought into Almas’s own Fabric, and where a source supports it, mirrored rather than copied out.

Row-level security by role

A person’s role decides what data they can reach: the firm’s whole book for management, a narrower slice for an analyst, their own accounts for a dealer. A request that reaches beyond it returns nothing and says so.

Every answer leaves a trail

Each question is kept with the plan, the SQL, the rows and the answer, against the person who asked. Refused requests are kept too, with the reason.
